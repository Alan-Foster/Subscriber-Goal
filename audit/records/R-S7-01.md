# R-S7-01: Background jobs holding the community-wide lock block moderator goal creation

**Problem · suspected** · criticality 7/10 · areas 7.04, 7.02, 2.03, 8.07 · paths C8-community-mutation-lease, C4-create-classic

> Audit record. Generated from `audit/records/R-S7-01.json` by `npm run audit:records`; edit the JSON, not this file. To turn it into an issue, follow `audit/issue-template.md`.

## 1. Current Implementation

When a moderator submits the create-goal form while posts-updater work holds the community-wide lock, creation fails immediately with an 'already in progress' message. Deletion waits up to 4 s, then fails the same way.

## 2. Problem and evidence

One lock, subscriber_goal_community_mutation_v1_lock, is taken at 13 call sites, including work run by posts-updater-job every minute (completed-goal cleanup, highlight reconciliation, app repair, scheduled-post displacement, source-post deletion, onboarding). Manual creation passes no retry option. The lock's 60 s TTL (userFacingLockTtlMs) can outlive a job killed at the 30 s request limit. Characteristics: A, D.

**Location:** src/server/core/communityGoalMutation.ts:44 (withCommunityGoalMutationLease); src/server/core/createSubscriberGoal.ts:340; src/server/triggers/scheduler.ts:73; src/server/routes/internalUi.deleteGoal.ts:39; src/server/utils/lockTtl.ts:24

**Observed outcome:** Reported by the maintainer: form progression appears stuck while the cron job runs. Not yet confirmed in logs.

**Unverified assumptions:**

- That job phases hold the lock long enough to collide with moderator actions in practice.
- That Devvit doesn't separately queue requests behind a long-running scheduler request (not checked in the docs).
